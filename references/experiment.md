# 外部实验指南 · MVP 0.1.0

用本指南测试：这个 harness 能否在项目推进过程中持续保留体验关注，按节点改变职责，并影响有依据的设计决策。报告长度、建议数量和措辞完整度不算效果证据。

## 最小实验

选一个正在推进、有具体用户任务的真实项目。保留当前版本，限定一个旅程和少数体验目标；先做分析，只有原任务已授权时才修改原型或产品。无需为完成实验扩大实施范围。

1. 将完整产物交给外部 Agent，按 `SKILL.md` 激活，提供项目目标、当前材料、允许动作和状态文件位置。记录 Agent、模型、日期、工具及实际激活方式。
2. 在正常项目工作中继续推进。宿主 Agent 应自行在相关节点执行检查，无需用户每轮重复提醒“调用 harness”。保留每次检查的节点、依据、决定和状态变化。
3. 有适合暂停的时点时，在新会话中重新激活，并交给它同一份 `state.json`、`checkpoints.jsonl` 与所需项目材料。观察它是否准确恢复目标、未决问题、已拒绝方案和证据缺口。
4. 结束这一小段实验后，导出状态与检查记录，填写 `templates/RETURN-REPORT.md`。未发生、未检查或无法观察的部分，直接写“未测试”。

这是顺序推进的真实多轮实验。不要在一次回答里虚构六轮工作、用户反应或验证结果。脚本只负责记录和导出，不会自主唤醒模型；宿主中断后若未重新激活，不能宣称仍在监控。宿主不支持自动调用时，可记录人工提醒作为运行缺口，不能把它归为自动连续关注。

执行者另行维护一份独立事件清单：从实际项目变更、任务输入或人工记录列出相关与无关事件，填写预期节点、是否人工提醒、是否触发及结果是否可观察。不要仅从 harness 自己写出的 checkpoint 反推事件清单；它不能显示未触发的检查。用这份清单确定“应检查事件”的范围，再区分已检查、漏检、不可观察；无关事件也可用来检查是否正确跳过。覆盖分母或观察范围不完整时，覆盖率写“未知”，不要硬算。

## 在节点上观察什么

以下是需要覆盖的行为，不是每个项目都必须依次执行的六个步骤。一次事件可以关联多个节点，记录主要节点和检查先后关系即可。

| 节点 | 可观察的行为 | 值得记录的失败 |
|---|---|---|
| `intake` | 从当前目标和材料建立体验关注，分开事实、报告主张和假设 | 未看依据就套用固定策略；把文档建议当作用户事实 |
| `before-change` | 判断本次变更影响哪些目标与旅程；把相关取舍带入任务 | 遗漏已知约束；每次都从头全面评审；对无关变化提出新设计 |
| `after-change` | 检查具体修改及新问题；把尚未验证的问题保留为 `awaiting-validation` | 因为实现了建议或代码测试通过就宣布体验问题已解决 |
| `feedback` | 根据新证据、用户目标改变或方案拒绝修订策略，并保留理由 | 把拒绝改写成接受；反复推荐已否决方案；把旧目标当作新要求 |
| `resume` | 用持久状态恢复关注，并核对版本与证据是否仍适用 | 遗忘未决问题；使用过时证据；假称中断期间已做检查 |
| `handoff` | 明确当前结论、未决项、下一次检查条件和接续位置 | 只交报告；遗漏待验证问题；把临时判断写成最终验收 |

问题状态使用 `open`、`in-progress`、`awaiting-validation`、`resolved`、`deferred`、`dismissed`。检查恢复后状态是否仍有依据；`deferred` 和 `dismissed` 应保留原因与适用条件。重开问题应关联原问题，而不是重复创建一条互不相关的新建议。

## 自然事件与受控检查

优先观察实际发生的变更和反馈。若实验期内没有出现某种事件，可以由实验执行者一次提供一个受控输入，例如“假设此次只更新构建说明”，或明确指定一个临时的目标变化情境。每次标为 `controlled-fixture`，与实际项目事件 `natural` 分开；上一轮结束后再给下一项。

受控输入可以测试判断和状态流转，不能证明真实用户遇到了问题、接受了方案或体验得到改善。不要为了覆盖节点伪造用户反馈，也不要把临时测试目标覆盖成项目的真实目标。可在隔离的状态副本中做受控检查，结束后保留副本和标签。

建议关注三个有区分度的事件：

- 一个与当前体验目标相关的变化：是否及时复查相关证据，提出具体策略或保持原策略？
- 一个无关变化：是否给出有依据的简短“不需体验修订”，避免扩大任务？
- 一次用户实际改变目标或拒绝方案：是否修订取舍，并在后续轮次保持一致？没有真实事件时，明确标注受控检查。

## 判断“有帮助”的依据

挑出 1–3 条实际决策轨迹：触发变化 → 当时证据 → 策略判断 → 执行或不执行的动作 → 后续观察。说明 harness 新增了什么信息或改变了什么决定；没有改变也如实记录。只有建议时，结论止于“提出了可检验建议”。

依据分别标记 `observed`（实际观察）、`reported`（来源报告）、`hypothesis`（推断待验证）；证据类型使用 `document`、`observation`、`user-report`、`runtime-test`、`simulation`。实际观察到 Agent 的行为，不等于观察到了终端用户的体验改善。

检查记录至少要回答：

- 它是否发现了原流程会遗漏的具体问题？这一判断有什么对照或依据？
- 建议是否进入了任务，产生了可指出的差异？是否增加了不必要功能或返工？
- 问题关闭依据是否匹配原来的体验目标？验证范围外的结论是否仍被保留为未知？
- 哪些检查漏触发、重复触发或依赖用户提醒？跨会话恢复是否准确？
- 新证据是否使原建议被缩小、撤回或重新打开？

若没有比较流程，不推断“比原 Agent 更好”。可选地，在同一基线和任务上比较普通评审与 harness：尽量保持模型、工具和额外时间或调用预算相当，事先固定要观察的任务结果，把状态维护成本也计入。不要让后运行的一组直接复用前一组结论；单个案例只提供局部证据，不支持通用提升幅度或因果保证。

## 回传

使用回传模板保存独立可理解的报告；脚本导出的骨架可作为底稿，保留状态和检查记录作为证据索引。报告优先包含具体决策、错误与缺口，无需复制整个聊天记录。

只纳入本次测试允许评估的材料；外发前使用最少必要片段与可共享引用，不自动打包账号资料、私有项目全文或无关聊天。无法共享的证据可以给出脱敏摘要和限制说明。真人判断留给真实参与者填写；缺席时留空，不由 Agent 代写。
